# Panel P6.4 — Mobile Hardening & Parity Design

**Date:** 2026-08-09  
**Status:** approved by user in design review  
**Branch:** `feature/panel-p6.4-hardening-parity` from `origin/main` (`b4c36a1`)  
**Predecessors:** P6.1 [#106], P6.2 [#108], P6.3 [#112]

## 1. Goal

Close the mobile-companion initiative with one focused hardening PR: remove the
known phone correctness and accessibility gaps, make every Tier-2 surface
honestly usable at 390×844, add a deterministic mobile Playwright acceptance
path, and prevent performance regressions with a blocking bundle budget.

This phase proves code, CI, and browser behavior. Physical-device acceptance is
kept separate and explicitly reported as a pre-production gate; it is never
silently inferred from Chromium emulation.

## 2. Locked scope decisions

The user approved these boundaries during the 2026-08-09 design review:

1. One focused PR, internally split into independently testable tasks.
2. Fix confirmed user-visible correctness, UX, accessibility, and test-reliability
   gaps. Cosmetic refactors, dead-prop cleanup, and minor markup deduplication do
   not enter the phase merely because they were mentioned in an older review.
3. `/me` gets a navigation entry only for the active tenant's `staff` role.
   Owners/admins/managers keep their current navigation. The route remains
   directly reachable without a new route-level role redirect.
4. The deterministic bundle-size budget is blocking. Lighthouse Mobile is
   reproducible and archived but advisory, so noisy score variance cannot flap
   an otherwise-correct PR.
5. Real iOS Safari, Android Chrome, KMP QR scanning, and cellular/SSE behavior
   remain explicit `NOT RUN` gates until exercised on physical devices.

## 3. Non-negotiable project constraints

- One adaptive cutover only: Tailwind `md` (768px). The reference phone is
  390×844. No `/m/*` routes, user-agent detection, or new breakpoints.
- Tailwind reflow before JS. `useIsMobile()` remains the only sanctioned viewport
  query and is used only at true presentation swap points.
- UI primitives live in `@idento/ui`; the panel does not reimplement them.
- Every panel-facing string lands in both EN and RU in the same change.
- `@idento/ui` has no i18n dependency; all strings enter primitives through
  props.
- Semantic color tokens only; both light and dark themes are mandatory.
- Phone-only interactive targets are at least 44×44 CSS pixels.
- No backend, migration, or OpenAPI/schema change is required or allowed.
- Tier-3 authoring/hardware screens remain behind `DesktopOnly` on the same URL.
- No service worker or offline web mode; offline operation stays in the KMP app.

## 4. Architecture

P6.4 has four layers, executed in this order so every later acceptance test is
written against already-correct primitives and states.

### 4.1 Shared primitive hardening

#### `SheetContent`

`packages/ui/src/components/sheet.tsx` gains an optional `hideClose?: boolean`
prop, matching the existing `DialogContent` convention. The Radix close button
is not mounted when `hideClose` is true; Escape/outside-click behavior remains
owned by the caller through the existing Radix content props.

`CheckInConfirmSheet` passes `hideClose={checkin.isPending}` in addition to its
existing `onOpenChange`/Escape/outside guards. While check-in is pending there
is therefore no misleading X affordance that appears clickable but cannot
dismiss the sheet. Once the mutation settles, normal dismissal returns.

#### `QrDisplay`

`packages/ui/src/components/qr-display.tsx` stops owning English copy. Its API
adds required `codeLabel` and `expiresInLabel` string props. Every panel
consumer passes translations from the existing i18n boundary; EN and RU keys
land together. The generic accessible QR label remains credential-free.

The visual countdown continues updating once per second, but it is no longer a
per-second polite live region. The timer stays available to assistive
technology through its accessible label, while the transition to the expired
state is the meaningful `role="status"` announcement. Regenerate and other phone text actions receive
`min-h-11`/equivalent 44px hit areas without changing desktop density outside
the full-screen mobile primitive.

### 4.2 Panel correctness and Tier-2 parity

#### Readiness overflow

`ReadinessStrip` keeps its horizontally scrollable chip row but gains a bounded,
`min-w-0` outer containment layer. The chip scroller may overflow internally;
the document body may not. A component regression test pins the containment
classes and the mobile Playwright suite asserts
`document.documentElement.scrollWidth === document.documentElement.clientWidth`
on a seeded event with labels/counts wide enough to reproduce the former
489px-on-390px failure.

#### Monitor truthfulness

`EventTabBar` remains cache-only (`enabled: false`) and must issue zero monitor
requests. Station age is evaluated at
`Math.min(Date.now(), snapshot.dataUpdatedAt)` so a snapshot that stopped
refreshing after the user left Monitor cannot manufacture a stale-station dot
from elapsed wall time alone. The existing 10-second local tick remains only as
render bookkeeping while the cache is actively refreshed.

Tests pin both properties: no fetch from the tab bar, and no false attention dot
after wall time advances beyond the station threshold on an unchanged cache.

`MonitorPage` continues rendering last-known-good event and snapshot data after
a failed background refetch. A regression test first renders successful data,
then forces a refetch error and proves the event title/cards remain. Initial
load failure remains an honest error state. Stale-data dimming applies only to
real snapshot content; the no-snapshot error card is never wrapped in reduced
opacity. Stream-state announcements remain limited to state transitions, not
the ticking “updated N seconds ago” counter.

#### Staff-only self-service navigation

`AppShell` and `NavDrawer` use the active tenant membership query—the same live
tenant-role source already used by `StaffPage`, never the cached global user
role. They render “My profile” → `/me` only when the resolved role is exactly
`staff`. Loading/error fail closed by omitting the link. Desktop and mobile
navigation use the same decision and EN/RU key.

The `/me` route remains a normal protected route for deep-link compatibility;
no redirect or backend authorization behavior changes.

#### Tier-2 reflow and shared states

The browser sweep covers the Tier-2 contract from the parent mobile spec:

- Organization: single-column, padded form/read-only card within the viewport;
  no fixed structural width and no clipped save/error state.
- Event creation: Dialog content, fields, validation, and actions fit at 390px;
  keyboard focus remains inside the dialog and returns to the trigger.
- Event general information: the existing Overview/header is the read-only
  phone view; no duplicate settings route or editor is introduced.
- Error, empty, loading, and retry states on Tier-1/Tier-2 screens fit without
  body overflow and never collapse a network error into “no data”.

Only defects reproduced by the sweep are changed. Tier-3 screens remain gated,
and the sweep verifies their gate rather than adapting their authoring UI.

#### Small confirmed correctness gaps

- `AttendeeCard` omits the organization separator when `company` is empty.
- `DesktopOnlyGate` screen heading semantics expose an `h1` at the page level;
  descriptions and actions do not begin the document outline at `h2`.
- Pending destructive actions remain disabled and cannot be submitted twice.

### 4.3 Deterministic test reliability prerequisite

The pre-change full panel baseline on `b4c36a1` produced one known load-sensitive
failure in `StaffCard.test.tsx`:

`session-ref cancel race: closing the confirm dialog mid-flight...`

The test uses a fixed 40ms MSW delay and assumes the response is still pending
after two `user.click()` calls. Under full-suite load the 40ms can elapse before
Cancel, legitimately opening the print sheet; in isolation the file passed
26/26. Production session-ref behavior is not implicated.

P6.4 replaces the fixed timing window with a manually released request gate:
the test arms the pending response, confirms Cancel, then releases the response
and asserts unconditional token caching without sheet opening. No production
logic changes for this stabilization. Final verification requires two
consecutive green full panel runs so the hardening phase does not ship on a
known flaky baseline.

## 5. Mobile Playwright acceptance

### 5.1 Project isolation

`panel/playwright.config.ts` defines two Chromium projects:

- `chromium`: existing desktop device settings and existing specs; explicitly
  excludes `mobile-companion.spec.ts`.
- `mobile-chromium`: exact viewport 390×844 with touch/mobile context; runs only
  `mobile-companion.spec.ts`.

This prevents every existing desktop/a11y spec from being silently doubled.
Both projects reuse the current real-backend seed infrastructure.

### 5.2 Mobile journey

The new spec seeds a ready event, attendees in checked-in/not-checked-in/blocked
states, assigned staff, monitor stations, and provisioning capability through
the real backend API. It then exercises:

1. Login/session entry and Home.
2. Event Overview and readiness strip.
3. Monitor, including live → reconnecting/error presentation through controlled
   network interruption without pretending a physical cellular test occurred.
4. Attendee search → card → manual check-in → undo → block/unblock.
5. Staff QR full-screen display.
6. Station provisioning QR and regeneration.
7. Staff `/me` navigation using a staff-role session.

The functional journey runs once in light theme. A focused parity pass checks
the key Overview/Monitor/Attendees/Staff/QR states in both light and dark to
avoid duplicating every mutation.

### 5.3 Browser assertions

At each applicable checkpoint the suite asserts:

- document width equals viewport width;
- phone-only interactive targets are at least 44×44;
- Axe reports no WCAG A/AA violations for the rendered state;
- Dialog/Sheet focus is trapped and returns to its trigger;
- error states remain distinguishable from empty states;
- QR bearer values returned by the seed/mutation are absent from DOM text and
  accessible names (the visual SVG encoding is expected);
- light and dark states keep semantic status icon + text + color.

The mobile project becomes part of the required `ci-success` path after its
suite is green in the P6.4 PR. The prior “soft while proving stability” period
ends with this hardening phase; artifacts remain uploaded on failure.

## 6. Performance budget

### 6.1 Blocking deterministic budget

Measured production baseline on `b4c36a1`:

- initial JavaScript: 1,474.16 kB raw;
- initial JavaScript: 417.40 kB gzip;
- CSS: 57.54 kB raw / 11.13 kB gzip.

A dependency-free Node script runs after `npm run build -w panel`, locates the
emitted initial JS asset, computes raw bytes and gzip bytes with `node:zlib`, and
fails when either limit is exceeded:

- raw JS ≤ 1,550,000 bytes;
- gzip JS ≤ 430,000 bytes.

The limits allow small hardening copy/test glue while preventing unnoticed
dependency or bundle expansion. Asset absence or multiple ambiguous initial
entry assets is itself an error; the script never silently skips the check.
The budget is wired into the blocking panel build/validation path in CI.

### 6.2 Advisory Lighthouse Mobile

Lighthouse Mobile runs three times against the built/served panel and records
the median report. Authentication uses a reproducible setup step against the CI
backend rather than a developer's browser profile. Reports are uploaded as CI
artifacts.

Advisory targets:

- Performance ≥ 80;
- Accessibility ≥ 95.

Missing reports or tool crashes are visible in the job summary, but Lighthouse
scores do not fail `ci-success`. Deterministic bundle and Playwright/a11y gates
remain the merge blockers.

## 7. Error and data-state policy

- A request error never renders the same copy or component as a legitimate
  empty result.
- Background refresh failure retains already-rendered verified data and marks
  it stale; it does not blank the page.
- Initial failure with no verified data renders an error and retry/back action.
- SSE reconnecting and terminal error are distinct states. Browser simulation
  validates UI semantics only; it is not claimed as cellular acceptance.
- Pending mutations gate every applicable dismiss or repeat-submit path.
- Bearer QR tokens remain React state only, are never persisted, and never
  appear as plain DOM/accessibility text.

## 8. CI and verification

Required automated gates:

```bash
npm test -w @idento/ui
npm run typecheck -w @idento/ui
npm run lint -w @idento/ui
npm test -w panel
npm run typecheck -w panel
npm run lint -w panel
npm run build -w panel
npm run check:bundle -w panel
npm run e2e -w panel
```

Before phase completion:

- the full panel Vitest suite passes twice consecutively;
- shared UI suite/typecheck/lint pass;
- panel typecheck/lint/build/bundle budget pass;
- desktop and mobile Playwright projects pass against the real seeded backend;
- a controller-run 390×844 browser walk covers both themes and records any
  deviation in `.superpowers/sdd/progress.md`;
- Lighthouse median and reports are recorded as advisory evidence.

## 9. Physical pre-production gates — explicitly not merge blockers

These remain `NOT RUN` until performed on real devices:

1. iOS Safari: safe-area, installed PWA chrome, focus/keyboard behavior.
2. Android Chrome: touch behavior, installed PWA chrome, QR brightness.
3. KMP app scans staff-login and station-provisioning QR codes from the phone.
4. SSE behavior across real cellular/venue Wi-Fi transitions.

They must be reported separately from browser/CI acceptance. P6.4 may be merged
with these gates open, but the mobile companion is not called physically
accepted until they pass.

## 10. Out of scope

- Backend/API/schema work.
- KMP, desktop kiosk, printer, or hardware-agent changes.
- Physical ZD410, Tauri lifecycle/update, or kiosk-lockdown acceptance.
- Service worker, offline web behavior, push notifications.
- Adapting Tier-3 authoring/hardware screens for phones.
- New routes or breakpoints.
- Broad route-level code splitting unless the approved bundle budget cannot be
  met without it.
- Cosmetic dead-prop cleanup, markup deduplication, and unrelated refactors.
- Staff sign-in liveness; the backend contract still does not expose it.

## 11. Implementation roadmap

The implementation plan will split the PR into independently reviewable tasks:

1. Stabilize the pre-existing `StaffCard` pending-response test gate.
2. Harden `SheetContent` and `QrDisplay`, including localized props and a11y.
3. Fix `ReadinessStrip`, monitor cache/error semantics, heading hierarchy, and
   the attendee separator.
4. Add staff-only `/me` shell navigation and complete the Tier-2 390px sweep.
5. Add the isolated mobile Playwright project, seed, journey, overflow, touch,
   focus, Axe, theme, and secret-hygiene checks.
6. Add blocking bundle budget and advisory Lighthouse artifacts; promote the
   stable E2E acceptance path in CI.
7. Run final automated gates and the two-theme browser walk; append the ledger
   with browser results and the four still-open physical gates.

## 12. Phase exit criteria

P6.4 is browser/CI complete only when all of the following are true:

- no body-level horizontal scrolling at 390px on every Tier-1/Tier-2/gated
  route exercised by the acceptance suite;
- the full mobile journey passes in CI;
- touch, focus, Axe, theme, and QR-secret assertions pass;
- EN/RU parity includes every new primitive and shell string;
- initial JS remains within 1,550,000 raw / 430,000 gzip bytes;
- Lighthouse median is captured with targets reported, not fabricated;
- all required unit/type/lint/build/E2E gates are green;
- physical gates are listed honestly as pass/fail/`NOT RUN`.
